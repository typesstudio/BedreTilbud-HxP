## 2. Message lifecycle: introduce “draft” instead of auto-send

Right now your flow is conceptually:

> Incoming email → AI generates reply → send via Resend → save message → show in UI

You want:

> Incoming email → AI generates **draft** reply → store as draft → user approves → send → mark as sent

### DB changes (Supabase `beskeder` or equivalent)

Add:

* `role` (if not already): `'company' | 'user' | 'ai' | 'system'`
* `status`:

  * `'received'` – inbound from company
  * `'draft'` – AI suggestion waiting for approval
  * `'sent'` – actually sent to company
  * `'failed'` – send failed
* `source_type` (optional): `'ai' | 'human'` (so we can distinguish AI draft vs user-typed reply)
* `debug_meta` JSONB (for later debug info)

A typical pair will be:

* Company message: `role='company', status='received'`
* AI draft: `role='ai', status='draft'`
* Final sent: same row updated to `status='sent'` (or a new row `source_type='human'` if user rewrote the text completely).

## 3. Backend orchestration: split “generate” and “send”

### 3.1. AI reply generator (no sending)

Your IMAP / incoming-email flow (currently in n8n) should **stop sending** the AI reply itself.

New behaviour:

1. Incoming email → you create the company message in `beskeder`.
2. n8n calls your backend `POST /ai-messaging/generate-reply` (or directly an OpenAI call if you keep it in n8n), with:

   * `thread_id`
   * `company_request_id`
   * Last company message text + meta (CPR, missing PDFs, MitID, etc.)
   * Full conversation context (if needed)
3. The AI generates **only** a reply **text**, plus some tags (see debug section).
4. Backend (or n8n) writes a new message:

   * `role='ai'`
   * `status='draft'`
   * `body = <ai reply>`
   * `source_type='ai'`

No email is sent yet.

### 3.2. “Send message” endpoint

Frontend needs an API to trigger the actual send:

`POST /messages/:id/send`

Behaviour:

1. Check that the message:

   * belongs to the current user / thread
   * has `status='draft'`
2. If the user edited the text in the UI, take that new body instead of the original.
3. Call Resend with:

   * To: insurance company email
   * From: thread-specific address (`thread_id@bedretilbud.com`)
   * Subject: from original thread or system logic
   * Body: final text
4. Update the message row:

   * `status='sent'`
   * `sent_at=now()`
5. If Resend fails:

   * `status='failed'`
   * Store error in `debug_meta.send_error`

Optional: create a separate `user` message if they typed something from scratch instead of using the AI.

## 5. Messaging debug system: see what’s going on

Now the fun part: a **debug layer** that uses the same AI to critique itself.

Goal:

* For every pair: **company message ↔ AI reply**, you get:

  * What type of request it was
  * Did the AI answer the question?
  * Did it mention CPR if needed?
  * Did it ask for PDFs instead of just MitID?
  * Tone, length, clarity
  * Suggestions for prompt improvements

### 5.1. Data model

New table `message_debug_reports` (or reuse `debug_meta` on messages with a structured schema):

* `id`
* `company_message_id`
* `ai_message_id`
* `final_sent_body` (if user edited)
* `analysis` JSONB, e.g.:

  ```json
  {
    "intent": "request_for_offer_with_missing_pdfs",
    "answered_all_questions": true,
    "mentioned_cpr": false,
    "mentioned_pdf_requirement": true,
    "mentioned_mitid_only": false,
    "tone_score": 0.9,
    "length_ok": true,
    "issues": [
      "Should explicitly ask for CPR number if not present",
      "Could be shorter in the second paragraph"
    ],
    "prompt_suggestions": [
      "When CPR is needed and not already stated, always add a clear, single-sentence request for CPR.",
      "If company only links to MitID, tell them kindly you need the full PDF attached to this email."
    ]
  }
  ```

### 5.2. When to run the debug analysis

Best: **right after a message is sent** (so you analyse the actual outgoing text, including user edits).

Flow:

1. `/messages/:id/send` → after successful send, enqueue a job (n8n or backend worker).
2. Worker calls an **AI Debug Agent** with:

   * Last company message text
   * AI draft text
   * Final sent text (maybe same as draft, maybe edited)
   * Conversation context (optional)
3. Debug Agent returns the structured JSON analysis.
4. Save to `message_debug_reports` (or in `debug_meta` on the AI message).

## 7. Multi-agent thinking baked in

To keep it scalable and robust, structure your AI layer as **three logical agents**:

1. **Classifier Agent (no user-facing text)**
   Input: last company message, context.
   Output (JSON only):

   * `intent` (enum): `missing_pdfs`, `mitid_only`, `general_question`, `need_cpr`, etc.
   * `must_ask_for_cpr`: boolean
   * `must_request_pdfs`: boolean
   * `should_answer_technical_question`: boolean
   * `risk_flags`: e.g. `["mentions_other_insurance_companies"]`

2. **Reply Agent**
   Input:

   * User-facing system prompt
   * Classifier output
   * Company + thread context
     Output: **Danish email text only** (no JSON), respecting rules:
   * Answer their question first
   * Then ask for missing PDFs if needed
   * Then mention CPR if needed
   * Never mention “we compare with others” etc.

3. **Debug Agent** (for the reporting system)
   Input: company message, classifier result, AI reply, final sent text.
   Output: the `analysis` JSON described above.

These can all still be implemented with one LLM, but logically separate prompts keeps it maintainable.

## 8. Iteration loop: how you’ll actually use this

Here’s how you run your manual lab with one user:

1. **Enable manual mode for you**

   * `ai_messaging_mode='manual'` on your test account.

2. **Real-world testing**

   * Insurance companies reply as usual.
   * AI drafts show up in the thread.
   * You:

     * Approve as-is
     * Or tweak wording
     * Or reject and write your own

3. **Review debug reports**

   * Once per day, go into `/admin/messaging-debug`.
   * Look at:

     * Where AI missed CPR
     * Where it failed to ask for PDFs
     * Where tone or clarity is off

4. **Adjust system prompts**

   * When you see recurring issues, update:

     * Classifier prompt (better tags)
     * Reply prompt (stronger rules)
   * Optional: keep a `PROMPT_VERSION` in `debug_meta` so you know which version produced which behaviour.

5. **Move towards partial automation**

   * Later, you can add a confidence threshold:

     * If Debug Agent predicts “high quality, no critical issues” → auto-send for low-risk intents.
     * Else → keep manual approval.
