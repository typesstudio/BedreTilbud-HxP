## 3. Debug the “Hus, Bil” label

The line “Sammenlignet: Hus, Bil” is wrong because there is no Bil in your PDFs.

This label is usually derived either from:

* `comparison_json.policyPairs[*].currentPolicy.type / offerPolicy.type`, *or*
* a union of `policy_type` from snapshots or health checks.

Given your history (earlier test data probably had a car policy), I suspect:

> The offers overview is building the list of policy types per company from **all historical comparisons / health checks for that company**, not just from the current offer’s comparison.

So if you once tested with a car insurance:

* Old health checks / old comparisons have `policy_type = 'bil'`.
* The aggregation code now does something like:

  ```ts
  const policyTypes = Array.from(new Set(
    allComparisonsForCompany.flatMap(c => c.policyTypes)
  ));
  ```

→ You get `['hus', 'bil']` even though the *current* comparison only has `hus`, `indbo`, `ulykke`.

### 3.1. Confirm in data

Run:

```sql
-- Any 'bil' policies for this user?
SELECT DISTINCT policy_type, company_id
FROM offer_snapshots os
JOIN documents d ON os.document_id = d.id
WHERE d.user_id = 'e85ec3b9-e354-4c49-9f68-194830e356af';
```

If this returns a row with `policy_type = 'bil'`, that’s from an old test document.

Also check whether `"bil"` appears inside `comparison_json`:

```sql
SELECT id
FROM company_comparisons
WHERE user_id = 'e85ec3b9-e354-4c49-9f68-194830e356af'
  AND comparison_json::text ILIKE '%"bil"%';
```

* If it **does not** appear in `comparison_json`, but appears in the UI, then the UI is **not** using `comparison_json` to build that label – it’s using some other, older data source → fix frontend.
* If it **does** appear in `comparison_json`, then Phase 1 extraction mis-labelled something; fix the extractor and re-run comparison.

### 3.2. Fix how “Sammenlignet” is computed

On the **offers API** (`/api/offers/user/:userId`):

* Find where `policyTypes` / `comparedTypes` / `comparedCoverages` is computed for each offer card.

* Change the logic so that for each offer **we derive the types only from the latest `company_comparisons.comparison_json` row for that company + offer**, for example:

  ```ts
  const policyTypes = Array.from(
    new Set(
      (comparisonJson.policyPairs ?? []).flatMap((pair: any) => [
        pair.currentPolicy?.type,
        pair.offerPolicy?.type,
      ].filter(Boolean))
    )
  );
  ```

* Do *not* union across old comparisons or health checks.

* Optional: filter to a known set of types: `['hus', 'indbo', 'ulykke', 'bil', 'rejse']` to avoid weird junk labels.

After this, all three cards should show exactly the same types (hus, indbo, ulykke) because you use the same current and same structure for each company.

## 4. Putting it together – what I’d actually change

### Backend fixes

1. **Detail endpoint**

   * Add a dedicated endpoint if not already there, e.g.:

     ```ts
     // GET /api/company-comparisons/:id
     app.get('/api/company-comparisons/:id', async (req, res) => {
       const id = req.params.id;
       const comparison = await db
         .select()
         .from(companyComparisons)
         .where(eq(companyComparisons.id, id))
         .limit(1);

       if (!comparison.length || !comparison[0].comparisonJson) {
         return res.json({ data: null });
       }

       res.json({ data: comparison[0] });
     });
     ```
