## 1. Where the process is *most likely* breaking

Given the latest Replit log:

> “All 4 comparisons have exactly **1 policy (hus)** and no bil/indbo anywhere.”

that tells us:

* OCR + segmentation + snapshot creation **do** see indbo and ulykke (you’ve confirmed there are clean snapshots for those).
* But **Phase 3 (DeterministicMatcher)** is only producing a single match (hus↔hus).
  → Only that one pair is passed into ComparisonAgent.
  → `comparison_json` only has 1 `policyComparison`.

So for this LB offer:

* Expected: 3 matched pairs

  * fritidshus ↔ hus
  * ulykkes ↔ ulykke
  * indbo ↔ indbo
* Actual: 1 pair (hus only)

This almost always means:

* either the **current** indbo / ulykke snapshots are missing `structured_policy` (address/person)
* or the matcher’s scoring logic is too strict and refuses to match them.

So **Phase 3 is the broken step**, not Phase 4 anymore.

Separately, the detail page:

* Probably receives `comparisonJson` + `policyComparisons`, but still checks `if (!data.policyComparisons)` or uses the old JSON shape (`data.coverageItems`), so it falls into the “no comparison” branch even when there is 1 pair.

So the second broken step is **UI mapping of the new JSON schema**.

### Step 3 – Simplify matching logic for this MVP

Given your use case (1 current + 1 offer per type), you don’t actually need fancy heuristics for this first version.

In `deterministicMatcher`, after you group by `policyType`, do something like:

```ts
// Pseudocode
for each policyType:
  const current = currentPoliciesOfThisType
  const offer   = offerPoliciesOfThisType

  if (current.length === 1 && offer.length === 1) {
    // Simple, deterministic 1:1 match
    matchedPairs.push({ current: current[0], offer: offer[0], score: 1.0, reason: 'single-per-type' });
    continue;
  }

  // else fall back to address/person scoring when there are multiple of same type
```

That guarantees:

* For your test data (exactly one `hus`, `indbo`, `ulykke` on each side), you always get **3 pairs**, independent of structured_policy quirks.

You can keep the address/person scoring for more complex future cases, but unblock this product now.

## 3. Should we create a manual “golden” export from the PDFs?

Yes – that’s actually a clean way to de-risk everything:

1. **Create two JSON fixtures** in the repo under `test/fixtures/`:

   * `lb-current.json` for your current policy PDF.
   * `lb-offer.json` for the LB offer PDF.

   Minimal shape:

   ```json
   {
     "policies": [
       { "id": "cur-hus",    "type": "hus",    "annualPremium": 5000, ... },
       { "id": "cur-indbo",  "type": "indbo",  "annualPremium": 3000, ... },
       { "id": "cur-ulykke", "type": "ulykke", "annualPremium": 1000, ... }
     ]
   }
   ```

2. **Write a small test script** that bypasses OCR entirely and feeds these fixtures directly into:

   * deterministicMatcher
   * ComparisonAgent
   * the JSON builder that writes `company_comparisons.comparison_json`

3. Assert in code (Jest or a simple script) that:

   * The matcher returns **3 pairs**.
   * The comparison JSON has `policyComparisons.length === 3`.
   * The types in all pairs are exactly `hus`, `indbo`, `ulykke`.

That becomes your “benchmark”. Whenever you change matcher/agent in the future, you can run this script and see if someone accidentally breaks the perfect LB example.

Replit can absolutely help set this up – you just need to tell it explicitly: “don’t go through the upload flow, just create a test harness using these fixtures”.
