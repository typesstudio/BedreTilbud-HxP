### 2.2 Ensure a health check exists for a given snapshotId

This is the core bug discovered earlier:

* Comparisons use **policy snapshot IDs** (from `policy_snapshots`).
* Existing `health_checks.snapshotId` may still be tied to older tables (like `offer_snapshots`) or simply not be populated for these new snapshots.

Implement this behaviour in the backend (in the health-check route handler):

1. Given `snapshotId`:

   * Try to load an existing health check from `health_checks` for that `snapshotId` and current user.
   * If **found** → return it as JSON (matching the shape expected by the current health-check page).

2. If **NOT found**:

   * Load the snapshot row from `policy_snapshots` (or equivalent) and its raw OCR/structured data.
   * Call whatever orchestration / service is already used to build a “health check” (the same logic as the main “Forsikrings­tjek” feature, but scoped to a single policy).

     * `snapshotId` = the policy snapshot ID
     * `userId` = current user
     * `policyType` = the policy type if available (indbo / hus / ulykke)
   * Return the newly created health-check JSON.

3. Make sure auth is respected:

   * Only allow access if the health check’s `userId` matches the current user’s ID.

If there is still an old **foreign-key constraint** on `health_checks.snapshotId` that points to `offer_snapshots`, update the schema properly:

* Either:

  * migrate to `policy_snapshots` (preferred), or
  * temporarily drop the FK so we can store health checks for policy snapshots too.
