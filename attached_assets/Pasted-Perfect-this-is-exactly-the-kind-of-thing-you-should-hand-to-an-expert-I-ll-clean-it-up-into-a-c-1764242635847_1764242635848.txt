## 2. Detailed analysis for your expert

### Bug 1 – Overblik total = 127 kr, Ulykke = 223 kr

**Symptom**

* Overblik “Årlig potentiel besparelse” shows **127 kr**.
* The Ulykke health check card shows **223 kr** annual savings (which is correct based on that policy).

Those numbers should either be:

* equal (if only one policy is in the group), or
* Overblik = **sum of all individual policies**.

**Root cause**

* Overblik endpoint is reading from an **old cached field** – something like `policy_snapshots.healthCheckSummary` or a similar cache – which contains an older benchmark-based calculation.
* The **correct, latest numbers** live in `health_checks.result` (e.g. `result.cumulativeSavings.after12Months` or `result.potentialSavings.*`).
* Ulykke’s card uses the **new** field, Overblik uses the **old** one → mismatch.

**What to change**

* For the Overblik aggregation endpoint (the one that returns `totalAnnualSavings` / `annualPotentialSavings`):

  1. **Stop using** cached values from `policy_snapshots.healthCheckSummary` (or any “summary” column that isn’t updated by the new health check logic).
  2. **Instead**, for every policy in the same snapshot group:

     * Read the *latest* row from `health_checks` for that snapshot.
     * Take the field you use on the single-policy view, e.g.:

       * `health_checks.result.cumulativeSavings.after12Months` (or whatever you already trust in the card),
       * or `health_checks.result.potentialSavings.realisticYearly`.
  3. Sum those numbers to compute `totalAnnualSavings` for Overblik.
  4. Use the same field for both the per-policy card and the Overblik total, so they can never drift.

**Testing**

* Pick a snapshotGroup with at least one finished health check.
* Compare:

  * Ulykke health check card’s number.
  * Overblik’s total.
* With the fix, Overblik should equal the sum of the per-policy numbers.

### Bug 2 – Indbo shows “Besparelsesberegning kræver en nuværende forsikring”

**Symptom**

* Indbo is analysed (it has a health check), but the UI shows something like:

  > “Besparelsesberegning kræver en nuværende forsikring”
* No final savings DKK value is shown.

**Root cause**

* In the Indbo health check JSON, `potentialSavings.realistic` (or similar) is **0**.
* The enrichment logic that fills `annualPotentialSavings` treats **“0” as “valid value, no work needed”**, instead of “we didn’t manage to calculate anything”.
* Because it sees a defined value (0), the code **skips the benchmark enrichment** that would normally compute a realistic saving based on current premium vs benchmark.
* Result: `annualPotentialSavings` remains `null` / `undefined`, and the UI falls back to the error message.

**What to change**

* In the backend step that prepares the stored health check result:

  1. Treat `0` and negative savings as **“missing/invalid”** when deciding whether to run the enrichment.

     * Example rule:

       ```ts
       const hasValidRawSaving =
         typeof potentialSavings.realistic === "number" &&
         potentialSavings.realistic > 0;
       ```
  2. If `hasValidRawSaving` is false (including 0), run the **benchmark enrichment**:

     * Use current premium and benchmark price to compute a realistic annual saving.
  3. Only skip enrichment when there is a **positive** and explicit saving from the AI.

**Result**

* Indbo will get a calculated `annualPotentialSavings` value, and the UI will show a DKK saving instead of the error text.

### Bug 3 – “0 af 3 dækninger” even though policies exist

**Symptom**

* On Overblik, the “Din dækningsstatus” header shows “0 af X dækninger”.
* The table might show rows, but the **counter** acts as if there are none.

**Root cause**

* The UI layer counts coverages using something like:

  ```ts
  const totalCoverages = healthCheck.result.coverageRows.length;
  const goodCoverages = healthCheck.result.coverageRows.filter(...).length;
  ```

* For **user’s current insurances**, the `coverageRows` array is **never populated** in `health_checks.result`.
  The structured coverage lives only in e.g.:

  * `offer_snapshots.structured_policy.coverageDetails.mainCoverages`
  * maybe `extraCoverages`, etc.

* Because `coverageRows` is empty/undefined, the counter becomes “0 af 3 dækninger”, even though the raw coverage data exists elsewhere.

**What to change**

* When generating or saving the health check result for a policy:

  1. Map the structured coverage data into the health check format:

     ```ts
     result.coverageRows = mapStructuredCoverageToCoverageRows(
       structured_policy.coverageDetails
     );
     ```

     Where `mapStructuredCoverageToCoverageRows` turns your `mainCoverages[]` / `extraCoverages[]` into rows like:

     ```ts
     {
       coverageName: string;
       isIncluded: boolean;
       limit: string | null;
       recommendation: "good" | "can_improve" | "missing";
     }
     ```

  2. Save this on `health_checks.result` before persisting.

* Overblik and the per-policy views should then reuse `coverageRows` instead of poking into `structured_policy` directly.

**Result**

* The “X af Y dækninger” text will correctly reflect real counts, and you can later reuse the same structure for the detailed tables.

### Bug 4 – Fritidshus stuck at “Afventer analyse”

**Symptom**

* The Fritidshus policy shows “Afventer analyse” and never gets a health check result on the front-end.

**Root cause**

* In your orchestration code, you have something like:

  * `guessPolicyTypeFromCoverages(structured_policy)` returns `"hus"` for Fritidshus (because its coverages look like a normal house).
  * Later, you validate with something like:

    ```ts
    if (guessedType !== snapshot.policyType) {
      // abort or skip
    }
    ```

    where `snapshot.policyType` is `"fritidshus"`.

* Because `"hus" !== "fritidshus"`, the orchestrator **never runs** the health-check agent for that snapshot, so the UI correctly says “Afventer analyse” forever.

**What to change**

Two safe options:

1. **Relax the validation** so “hus” and “fritidshus” are compatible:

   ```ts
   const normalizedGuessed = normalizeType(guessedType);
   const normalizedSnapshot = normalizeType(snapshot.policyType);

   if (normalizedGuessed !== normalizedSnapshot) {
     // skip OR log, but don’t treat fritidshus as mismatch
   }

   function normalizeType(t: string) {
     if (t === "hus" || t === "fritidshus") return "hus";
     return t;
   }
   ```

2. Or, **explicit mapping**:

   * If `snapshot.policyType === "fritidshus"` and `guessedType === "hus"`, allow it and run the health check with type `"hus"`.

**Result**

* Fritidshus policies will flow through the same house health-check logic and will no longer be stuck at “Afventer analyse”.
