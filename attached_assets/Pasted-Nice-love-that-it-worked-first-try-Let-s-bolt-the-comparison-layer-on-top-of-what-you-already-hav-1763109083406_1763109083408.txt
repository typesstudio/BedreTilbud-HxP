## 1. Architecture for comparison

You already have:

* **Phase 1 – OCR → Policy JSON** (`PolicyExtractor`)
* **Phase 2 – Policy JSON → HealthCheck JSON** (`HealthCheckAnalyst`)

Now add:

3. **Phase 3 – Matching (backend or light AI)**

   * Take all policies for:

     * `side = "current"` (user’s existing)
     * `side = "offer"` (company offer)
   * Create **pairs** by `policyType` (hus, indbo, ulykke, bil, rejse).
   * Output a clean list of **matched pairs**.

4. **Phase 4 – ComparisonAgent (AI)**

   * Input: list of policy pairs, each with:

     * `policyType`
     * `current` (company, premium, healthCheck, coverageDetails)
     * `offer` (same)
   * Output: single **Comparison JSON** powering:

     * **Samlet** tab (total savings, main highlights, cumulative chart, “Forstå det med småt”)
     * **Per-policy tabs** (Indbo, Hus, Ulykke, Bil, Rejse) with:

       * Annual cost comparison
       * Highlights where offer is better/worse
       * Detailed coverage table (inkluderet/ikke inkluderet + beløb)
       * Missing info questions (mainly for offer)

Visually it keeps your existing components; we just feed them more structured data.

## 3. 1:1 policy matching logic (Phase 3)

You can do this in backend code (recommended) and only use AI as a fallback.

### 3.1 Simple deterministic matcher

Pseudo-logic:

```ts
for each currentPolicy in currentPolicies:
  candidates = offerPolicies.filter(p => p.policyType === currentPolicy.policyType)

  if candidates.length === 1:
    match(currentPolicy, candidates[0])

  else if candidates.length > 1:
    // try address/person heuristics:
    best = candidate with highest score:
      +1 if same address
      +1 if same insured person name
      +1 if same offerNumber or policyName substring
    match(currentPolicy, best)
```

If you have more policies on offer side than current side, some remain unmatched (you can still show them as “extra offer policies”).

Keep this outside AI if at all possible – easier to test.

```text
SYSTEM – BedreTilbud PolicyComparisonAnalyst (DK)

Du er en dansk forsikringsanalytiker.

Du modtager allerede analyserede policer fra to selskaber:
- currentCompany (kundens nuværende selskab)

Dit job er at sammenligne dem 1:1 pr. policetype og lave et JSON-output,

KRITISKE REGLER

- Svar KUN med gyldig JSON – ingen forklarende tekst.
- Sprog: ALT på dansk.
- Du må KUN bruge de data, der findes i inputtet.
```

```text
1) Beregn årlige totalpriser og besparelse (Samlet)
- totalCurrentAnnualPremium = sum af annualPremium for alle policyPairs.current.
- totalOfferAnnualPremium   = sum af annualPremium for alle policyPairs.offer.
- annualSavings = totalCurrentAnnualPremium - totalOfferAnnualPremium (kan være negativ).

2) Lav per-policy costSummary
- For hver policyPair:
  - currentAnnualPremium = current.annualPremium
  - offerAnnualPremium = offer.annualPremium

   - fjern specialtegn, punktum, komma, parenteser

3. For hver normaliserede nøgle:
```

## 6. Implementation notes & wiring

* **DB side**

  * Store:

    * `policies` (side, company, policyType, annualPremium, coverageDetails, healthCheckJSON)
    * `comparisons` (per company pair, with the ComparisonAgent output)
  * For “Samlet” tab, you just pull the Comparison JSON.

* **Frontend**

  * Reuse:

    * `AnnualSavingsCard` → `overall.annualSavings`
    * `CurrentVsOfferCards` → `overall.totalCurrentAnnualPremium` / `totalOfferAnnualPremium`
    * `HighlightsRow` → `overall.globalHighlights` (Samlet) or `policyComparisons[x].highlights` (per tab)
    * `CoverageTable` → `policyComparisons[x].coverageComparison.rows`
    * `MissingInfoList` → `policyComparisons[x].missingInformation`
    * `RecommendationsList` → `policyComparisons[x].recommendations`
    * `CumulativeChart` → `cumulativeSavings`

* **1:1 guarantee**

  * Because we base comparison on **healthCheck.whatsIncluded**, which you already forced to be a full 1:1 mapping from `coverageDetails`, you get:

    * **Policy-level 1:1** via `policyPairs`.
    * **Coverage-level 1:1-ish** via the normalised name union.
