- The comparison pipeline now runs and processes policies correctly (no silent filtering).
- New offer from **Tryg** (uploaded Nov 18) has `structured_policy` correctly populated on its snapshots.
- Older current policies (e.g. Svphil, uploaded Nov 11) have:

Because of this, the matcher still finds `0` matches for the Svphil vs Tryg test user, **not due to code bugs but due to data and architecture issues**.

Key findings from the debug:

1) **Health Check Orphaning (index-based matching)**
   - In `comparisonOrchestrator.ts`, snapshots and health checks are matched **by array index**, not by ID.
   - Pseudocode (current behavior):
     ```ts
     for (let i = 0; i < snapshots.length; i++) {
       const snapshot = snapshots[i];
       const healthCheck = uniqueHealthChecks[i];
       if (!healthCheck) {
         console.warn(`No health check for snapshot ${snapshot.id}, skipping`);
         continue;
       }
       // ...
     }
     ```
   - If there are 3 snapshots but only 2 unique health checks, one snapshot (in our case, the important `hus` snapshot with metadata) gets dropped from comparison.
   - Health checks are currently linked via `documentId`, not `snapshotId`.

2) **Undefined database ordering**
   - Example: `getOfferSnapshotsByDocument(documentId)` does not use `orderBy`.
   - That means both snapshot ordering and health check ordering are not guaranteed.
   - Combined with index-based matching this is fragile and can lead to mismatched or dropped pairs.

3) **Legacy data limitation**
   - Current policies uploaded *before* the structured_policy fix have `structured_policy = NULL`.
   - They simply cannot participate in deterministic matching until re-uploaded or re-extracted.
